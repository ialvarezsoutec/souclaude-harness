Día 1, de cero a listo

  1. Ten git y Node ≥ 22.4. Nada más: no hay registry, ni .npmrc, ni token.
  2. Corre el instalador en la raíz del repo. npx github:ialvarezsoutec/souclaude-harness#v1
  3. Responde las cuatro preguntas — nombre, tipo, stack e idioma — o pásalas por flag y sáltate el modo interactivo.
  4. Conecta el Vault cuando lo pida (--vault-path si ya lo tienes clonado, --no-vault para omitirlo).
  5. Abre el repo con Claude Code. Lo primero que lee es CLAUDE.md y docs/constitution.md.
  6. Completa P7 y P8 de la constitución: son los dos principios que cada proyecto define por su cuenta.
Lo que NO tienes que hacer
  • Instalar skills a mano, una por una.
  • Copiar un CLAUDE.md de otro repo y editarlo.
  • Pedirle a cada persona del equipo que configure su máquina.
  • Mantener las reglas sincronizadas entre proyectos a mano.
El repo queda autosuficiente. Quien lo clona recibe el método completo — mismas skills, misma constitución, mismas reglas de Git.

Proyecto existente06 / 15

El mismo comando, tres puntos de partida

init

Repo legacy, sin harness

Cinco años de código y ninguna carpeta .claude/. El instalador solo agrega la superficie de Claude: no toca tu código, tus tests ni tu build.

Nada de lo tuyo entra en el plan.

adopt

Estructura hecha a mano

Ya tienes un CLAUDE.md y skills propias que armaste tú. No se escribe ni un archivo: solo se anota en el lockfile que lo que hay ya cuenta como harness.

Desde ahí, los upgrades funcionan normal.

upgrade

Harness de una versión vieja

Trae skills nuevas, reglas nuevas y corre las migraciones, que transforman lo viejo antes de comparar — así un fix antiguo aparece como un update normal.

Se invoca con /harness-upgrade.

Los tres son el mismo code path. No hay tres flujos con tres conjuntos de bugs: hay una sola tabla de veredictos, y es la de la próxima lámina.

Qué haces cuando aparece un .new

# 1 · ¿estoy al día? $ npx …#v1 status → salida 1: hay una versión nueva   # 2 · ¿qué cambiaría? $ npx …#v1 upgrade --dry-run   # 3 · aplicarlo $ npx …#v1 upgrade update .claude/skills/ccem-sdd/ conflict CLAUDE.md → CLAUDE.md.new
Desde Claude Code es un solo comando: /harness-upgrade. Corre status, luego el --dry-run, espera tu OK y recién ahí aplica.
El archivo .new

La propuesta queda al lado. Tú decides.

Cuando tu archivo difiere del que el harness querría emitir, no hay pisada y no hay merge automático: aparece <archivo>.new junto al tuyo y el original queda intacto.

$ git diff --no-index \ CLAUDE.md CLAUDE.md.new

Lees el diff, te llevas lo que sirve y borras el .new. Es una sugerencia, no una migración pendiente.

Los dos invariantes que sostienen esto en los tests: idempotencia — correr init dos veces no cambia nada la segunda — y pureza de --dry-run — el árbol queda byte-idéntico.

El ID del hito es el hilo

La roca nace en la reunión trimestral y se descompone en hitos. El hito emite el ID, y ese ID reaparece idéntico en cada eslabón hasta el release.

Roca · trimestreQ3Y26-REA
→
HitoREA-H3
→
Carpeta de specspecs/REA-H3-captura-lead/
→
Ramafeature/REA-H3-captura-lead
→
TasksREA-H3-T001…
→
PR · releasesquash & merge
Por qué importa

grep -r REA-H3 specs/ y git log --grep=REA-H3 devuelven lo mismo. Cualquiera puede reconstruir por qué existe una línea de código sin preguntarle a nadie.

Un hito puede producir varios specs: mismo ID, distinto slug. Cada carpeta es una rama y un PR.

La regla dura

Si no tienes el ID, pregunta. No lo inventes.

Sin ID no hay rama — los hotfixes incluidos. La urgencia cambia la prioridad, nunca el procedimiento. Si una rama o un release no tiene ID, la cadena está rota y se repara antes de seguir.

El día a día10 / 15

Tres frenos humanos antes de escribir código

spec.md→ ⏸ HUMANO→ plan.md→ ⏸ HUMANO→ tasks.md→ ⏸ HUMANO→ implement→ review→ PR

Hasta que los tres estén aprobados, la rama solo admite commits docs:. Durante implement el review es incremental, task por task — nunca en batch al final.

AgenteRol¿Código?
orchestratorDescompone, coordina y hace respetar los checkpoints.no
spec-authorRedacta spec, plan y tasks — una fase por invocación.no
implementerImplementa task por task, cada cambio con su test.sí
reviewerAprueba o rechaza. Sin herramientas de escritura: dictamina.no
La separación es el punto. Quien especifica no implementa, y quien implementa no se aprueba a sí mismo. Un reviewer sin permiso de escritura no es una recomendación: es enforcement.
Cuándo NO montar todo esto

Bug fix puntual, ajuste cosmético, spike, script one-off, hotfix o typo: se hace directo. Ceremonia que no sirve viola P9 — Simplicity First.

Para un cambio mediano existe la versión comprimida: /spec-new <ID> <slug> --lite. Mismos checkpoints, menos ceremonia.

EquipoV
Trabajo en equipo11 / 15

Dos repos con reglas opuestas, a propósito

Repo del proyecto

Todo cambio se revisa

  • Código, tests, specs y progreso.
  • Siempre rama + Pull Request. Nunca directo a main.
  • El coordinador hace el squash & merge.

Por qué: lo que entra al código pasa por revisión, sin excepciones y sin atajos por urgencia.

El Vault

El tablero refleja el ahora

  • Kanban, espejos de specs y progreso, rocas, evidencia.
  • Push directo a main, sin PR.
  • Repo aparte, para no ensuciar el del proyecto.

Por qué: si el tablero esperara a un merge, mostraría el pasado. Tiene que mostrar el ahora.

Nunca se cruzan: código, diffs y tests jamás van al Vault.
La ruta local vive en .claude/vault.local.json, que escribe el instalador.
Si el Vault no está configurado, el espejo se omite sin fallar. El trabajo local nunca se bloquea.

El anti-solapamiento

Si la tarjeta ya está en En curso con otro dueño, la está trabajando otra persona u otra máquina: paras y preguntas. No la tomas, no la mueves y no saltas a otra por tu cuenta.

Una tarjeta = una línea, así que dos personas nunca se contradicen al hacer merge: se conservan ambas.

La regla de honestidad

Si la herramienta no reporta el uso real de tokens, el orchestrator estima por tamaño de artefactos y lo marca como tal. Un estimado sirve para comparar celdas de la matriz e hitos entre sí — jamás se presenta como cifra contable ni de facturación.

El ritual · /rock-close

Al cerrar el trimestre se resume el JSONL y se ajusta la matriz si:

  • las escaladas superan el 10 % de los lanzamientos,
  • una celda concentra el rework — su tier quedó corto,
  • una celda nunca falla — puede bajar un tier.

Aprendizaje como ritual humano, sin ML: lo decide el equipo mirando los datos.
